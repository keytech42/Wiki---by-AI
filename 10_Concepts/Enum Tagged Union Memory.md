# Rust Enum (Tagged Union)의 메모리 레이아웃 원리

## 핵심 통찰
C언어의 Enum이 단순히 숫자(0, 1, 2)에 이름을 붙인 **상수화된 정수(const int)들의 집합**에 불과하다면, Rust의 Enum은 상태(Tag)와 추가 데이터(Payload)를 물리적으로 강제 결합하는 **대수적 데이터 타입(Algebraic Data Type)**이자 **Tagged Union**이다.

## 컴파일러의 지독한 최적화 로직 (사용자 리버스 엔지니어링)
1. **Tag의 가변성:** Enum은 현재 어떤 상태인지를 기억하기 위한 최소한의 공간(Tag)을 가진다. 상태의 수가 256개 이하라면 컴파일러는 `u8`(1 Byte)을 사용하지만, 이를 초과하면 자동으로 `u16`(2 Bytes) 등으로 펌핑하여 메모리 낭비를 극한으로 막는다.
2. **Payload와 정렬(Alignment) 규칙:** Enum이 품을 수 있는 다양한 상태 중 **'가장 큰 Payload'**를 기준으로 전체 메모리 구획이 정해진다. 또한 구조체와 완벽히 동일한 N배수 패딩(Padding) 룰이 적용된다.
3. **크기 고정의 마법:** 어떠한 상태를 가지든 간에 Enum의 전체 크기는 `Tag + 최대 Payload + Padding`으로 컴파일 타임에 **영구 고정**된다.

## 시뮬레이터 아키텍처 관점
파이썬처럼 상태에 따라 크기가 다른 객체를 힙(Heap)에 뗐다 붙였다 하는 짓은 캐시 미스의 주범이다. Rust의 Enum은 크기가 고정되어 있으므로 거대한 1차원 배열(`Vec`)에 일렬로 욱여넣을 수 있으며, 상태가 변해도 그 고정된 바이트 안에서 비트 값만 덮어쓰므로 성능이 압도적이다.

## 💡 세션 인사이트: "메모리 낭비입니까?" (Product vs Sum Type)
이 문서는 코드 작성 중 벌어진 **"왜 MacState의 모든 상태 크기를 다 합치지 않는가? 계산 실수인가?"**라는 사용자의 합리적 의심에서 출발했다.

### 1. 사용자 의문의 출발점 (오해와 직관)
시뮬레이터의 뼈대를 구성하는 아래 `MacState` 코드를 리뷰하던 중 의문이 발생했다.

```rust
pub enum MacState {
    Idle,                                     // Payload 0 byte
    Load { weight: f32 },                     // Payload 4 bytes
    Compute { weight: f32, activation: f32 }, // Payload 8 bytes
    Store { result: f32 },                    // Payload 4 bytes
}
```

- **오해:** "메모리 크기를 계산할 때 왜 전체 페이로드를 다 더해서 `Idle(0)` + `Load(4)` + `Compute(8)` + `Store(4)` = 16바이트로 합산하지 않는가? 계산 실수인가?"
- **답변:** 아니다. 한순간에 메모리 블록은 오직 '단 하나의 상태'만 가질 수 있다. 즉, `A AND B`가 아니라 `A OR B`이다.

### 2. 깨달음: 대수적 데이터 타입의 집합론적 매핑
- 사용자는 설명을 듣고 **"아, 배열 같은 병렬적 연결이 아니라 상호 배타적 선택지이기 때문에 집합론의 합집합(Union)이라는 용어를 쓰는구나!"**라는 수학적 본질을 짚어냈다.
- **구조체 (Product Type):** 교집합(AND). 두 필드를 모두 가져야 하므로 조합 경우의 수는 곱하기($2^{32} \times 2^{32}$)로 폭발한다.
- **열거형 (Sum Type / Disjoint Union):** 분리 합집합(OR). 경우의 수는 더하기($2^{32} + 2^{32}$)가 된다. 과거 C언어에서는 주소를 공유하여 이를 `union`이라 불렀고, Rust는 상태 식별표를 붙여 `Tagged Union`이라 부른다.

### 3. 하드웨어적 결론: O(1) 라우팅을 위한 의도된 메모리 낭비
컴파일러는 가장 큰 놈(`Compute` 8바이트)을 기준으로 **모든 상태의 크기를 12바이트(Tag + Padding 포함)로 획일화**한다.
만약 현재 상태가 `Idle`이라면 8바이트의 페이로드 공간이 완전히 낭비되지만, 컴파일러는 이를 기꺼이 감수한다. 
이 **'의도된 낭비'**가 있어야만 수만 개의 원소를 가진 `Vec`에서 `시작 주소 + (인덱스 * 12바이트)`라는 단 한 번의 O(1) 산술 연산만으로 목적지로 꽂힐 수 있기 때문이다. (포인터 점프 제거 및 공간 지역성 확보의 핵심 원리)

### 4. 세션 인사이트: "Enum의 기하학적 정렬(Alignment)과 이름의 소멸"
사용자의 추가적인 추론을 통해 다음 두 가지 사실이 완벽히 규명되었다.

1. **메모리 정렬(Alignment)의 기하학적 진실:** (관련 개념: [[Memory Alignment Padding]])
   단순히 가장 큰 Payload 크기로 전체를 맞추는 것이 아니다. 내부에 존재하는 **가장 큰 원자적 자료형(Primitive Type, 여기서는 `f32` = 4바이트)**의 정렬 규칙을 따라야 한다.
   - 구성: `Tag(1바이트)` + `Padding(3바이트)` + `Payload(8바이트)` = **총 12바이트**. 
   - 이 3바이트의 패딩은 메모리를 4의 배수로 정렬하여 CPU가 한 번의 사이클로 데이터를 안전하게 퍼올릴 수 있도록 강제하는 기하학적 완충 지대이다.
2. **이름의 소멸과 정수 식별자(Tag Index):**
   코드에 작성된 `Idle`, `Load` 등의 이름은 인간의 인지 능력을 위한 환상(Syntactic Sugar)이다. 컴파일이 끝난 바이너리 기계어에서는 이름이 완전히 증발하며, 메모리의 첫 바이트에 기록되는 `0x00`, `0x01` 같은 순수한 정수(Index)로만 남는다. CPU는 글자가 아닌 이 1바이트 정수를 읽고 산술적 분기(Assembly Jump)를 수행할 뿐이다.
